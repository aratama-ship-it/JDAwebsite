01 / Decision

実装前に固定する3つの判断

今回の合意「本番統合の設計で進める」を、実装時に解釈が揺れない粒度へ落としました。現在の推奨回答も併記しています。

1

写真フォルダ＋自動生成マニフェスト方式を採用する

Photoshopから公開用画像を書き出し、生成スクリプトが並び順・寸法・キャッシュ識別子を作る。HTMLへ写真を毎回追記しない。

推奨：採用
2

トップページを読み込むたびに自動表示する

初回ページの画像が表示可能になってから開く。閉じた後は既存ヘッダー内のランチャーから再表示でき、端末内には既読状態を保存しない。

推奨：毎回表示
3

現在の公開工程を確認してから実装を結線する

Git管理中のリリース工程と、未追跡のallowlist工程が併存しているため、どちらを正とするかを実装・コミット前のゲートにする。

必須ゲート
02 / State

確認済みと提案を混ぜない

既存ファイルから確認できた事実、今回の設計値、実装前に解消すべき点を分離しています。

確認済み 今回の提案 未確定・ゲート

確認済み

  • 本番は静的なHTML／CSS／JavaScript構成
  • ヘッダーは固定表示で、検索・SNS・メニュー操作が存在
  • 共通CSS／JSはトップ以外の複数ページでも利用
  • 試作はPCの縦2枚組、横1枚、スマホの1枚表示を実証済み

今回の提案

  • 公開用写真を専用フォルダへ配置
  • マニフェストをスクリプトで生成
  • モーダルはトップページだけで初期化
  • 全追加CSSを固有クラスへ限定

実装前の確認

  • 追跡中の現行リリース工程を正とするか
  • 未追跡のallowlist工程を統合するか
  • 最終的な写真枚数と容量
  • 公開用画像の目視承認
03 / Architecture

写真を足す作業を、壊れにくい一本の流れにする

静的サイトのブラウザは、サーバー上のフォルダ内容を安全・確実には列挙できません。そこで、フォルダを入力、マニフェストを表示用の契約として使います。

方式追加作業安定性判断
ブラウザでフォルダ一覧を取得 画像を置くだけ 静的ホスティングでは一覧取得を前提にできない ×不採用
HTMLへ写真を直書き 画像追加ごとにHTML編集 少数なら単純だが、更新漏れや順序ミスが起きやすい △予備案
フォルダ＋生成マニフェスト 画像配置後に生成コマンドを実行 寸法・順序・キャッシュを検証できる ●採用案
Photoshop公開用WebPを書き出す。PSDは入れない。
写真フォルダimages/competition-scenes/
生成スクリプト寸法・順序・ハッシュを取得。
manifest.json表示用の契約。altは人が管理。
トップページJSが取得し、モーダルを構築。
公開検証参照・容量・UIを確認。
04 / Files

ファイルの責任範囲

本番実装では以下だけを対象にし、既存スライダーや別ページの挙動を巻き込みません。

対象変更責任
images/competition-scenes/新規公開用画像と生成済みmanifest.jsonのみ。元写真やPSDは入れない。
scripts/build-competition-scenes-manifest.py新規対応画像だけを走査し、安定順・寸法・短いSHA-256・既存altを出力する。
index.html変更ヘッダーランチャーと空のモーダル骨格を追加。既存の大構造は組み替えない。
css/style.css変更.competition-scenes-*へ完全にスコープしたレスポンシブ表示。
js/main.js変更トップページに要素がある時だけ、取得・ページ編成・操作・アクセシビリティを初期化。
現行リリース設定／検証変更新規フォルダ・マニフェスト・参照整合性をリリース対象とテストへ追加。
未追跡allowlist工程保留利用する場合は画像パスと動的マニフェスト参照の検査を明示的に追加。既存案を上書きしない。
05 / Contract

表示データは最小限にする

大会名・日付・写真タイトルは表示しません。分からない情報を推測せず、画面上は写真と操作だけに集中させます。

{
  "version": 1,
  "images": [
    {
      "file": "001-stage.webp",
      "width": 1600,
      "height": 2000,
      "alt": "",
      "cache": "8f32ac91"
    }
  ]
}

ファイル名が並び順

001-、002-のような接頭辞で順序を固定します。生成のたびに既存のaltをファイル名で引き継ぎ、新規写真の説明は空欄のままにします。

生成時に拒否するもの

シンボリックリンク、隠しファイル、一時ファイル、PSD、TIFF、寸法が取得できない画像、不正な相対パス。

06 / Responsive

横長PCだけ、縦写真を2枚組にする

写真の向きは実寸で判断し、画面が狭い場合はすべて1枚ずつに戻します。元画像は常にトリミングしません。

表示環境縦写真横写真最後に縦1枚が残る場合
横長PC連続する2枚を同一ページに並べる横幅いっぱいに1枚表示中央に1枚表示
スマホ／縦長画面4:5フレームで1枚表示4:5フレーム内に1枚表示通常どおり1枚表示

制作基準：縦写真は1600×2000px（4:5／sRGB）。横写真は比率を保ち、長辺2000px以下を推奨。表示はobject-fit: containとし、余白だけを同じ写真のぼかしで補います。

07 / Behavior

待たせず、失敗しても本体を止めない

大会写真はトップページの追加体験です。読み込めない時に、既存サイトまで使えなくしない設計にします。

読み込みとフォールバック

  • マニフェスト取得上限は3000ms
  • 最初の表示ページをdecodeしてから自動表示
  • 次ページだけ先読みし、それ以降は遅延読み込み
  • 不正・空・取得失敗時は自動表示せずランチャーも隠す
  • 失敗時も既存トップページはそのまま操作できる

操作とアクセシビリティ

  • Esc、背景クリック、閉じるボタンに対応
  • 左右キー、ボタン、スワイプで写真移動
  • フォーカストラップと閉じた後のフォーカス復帰
  • 背景をinertにし、スクロールを固定
  • 動きを減らす設定では自動送りと遷移を停止
  • altは任意入力。画面には出さず、自動生成もしない
08 / Launcher

閉じた後は、既存ヘッダーから戻れる

新しい帯やヒーロー要素は増やさず、既存のヘッダー操作群へ写真サムネイル付きランチャーを追加します。

1440px以上

216×48px。36pxの先頭写真サムネイルと「COMPETITION SCENES／大会写真を見る」を表示。

1439px以下

44×44pxのサムネイルのみ。見た目の文字を省き、aria-labelで用途を伝える。

検索の展開中

ランチャーを非表示・操作不能にし、既存検索UIとの衝突を避ける。

09 / Release

公開工程の曖昧さを、実装前に止める

現在の作業ツリーでは、追跡中の既存工程と未追跡の新しいallowlist案が同時に見えています。どちらも勝手に正規化しません。

確認できた現行工程

scripts/prepare_release.pyとscripts/release_config.pyはGit管理中で、ルートHTML・CSS・JS・画像・external配下を組み立てる現在の基準です。

統合前に扱いを決める工程

deploy/jda-app.allowlistとscripts/build-jda-release.shは作業ツリーにありますが未追跡です。採用する場合は、動的に読むマニフェストと全画像をallowlist／検査へ追加します。

  • 採用する公開工程を明記する
  • マニフェストのスキーマと全参照ファイルを検証する
  • 共通CSS／JSのバージョン値を有効な全ページで更新する
  • 画像URLへ内容ハッシュを付け、古いキャッシュを避ける
  • 初回ページ合計1.2MB、各画像600KB以内を目標に確認する
  • ローカル成功と公開反映を分けて確認する
10 / Acceptance

本番統合の完了条件

見た目だけでなく、更新作業・失敗時・既存ページへの影響までを合格条件に含めます。

  • トップページでだけ、初回写真decode後にモーダルが開く
  • 閉じた後、ヘッダーランチャーから再表示できる
  • PCは縦2枚／横1枚、スマホは全写真1枚ずつになる
  • 写真タイトル・大会情報・イベントリンクを表示しない
  • 最初から最後までキーボードだけで操作できる
  • 取得失敗時に既存サイトの表示・操作を妨げない
  • 共通CSS／JSを使う他ページに見た目・挙動の回帰がない
  • フォルダ更新からマニフェスト生成・検証まで再現できる
  • モバイル390×844とPC1440×900で横はみ出しがない
  • コミット・push・公開は、それぞれ別の承認後に行う
11 / Phases

実装は4段階に分ける

各段階の結果を確認してから次へ進み、いきなり公開工程へ混ぜません。

本体と生成処理

公開用フォルダ、マニフェスト生成、トップページ骨格、スコープ済みCSS／JSを実装する。

リリース工程

正とする公開工程を確認し、新規アセットのコピーと参照検証を追加する。

候補版QA

PC／スマホ、画像向き、通信失敗、キーボード、既存ページ回帰、容量をローカルで確認する。

外部反映

差分レビュー後、コミット、push、デプロイ、公開URL確認をそれぞれ明示的な承認で進める。

12 / Design Memo

5つの問いへの回答

UIを足す目的と、残すもの・削るものを短く固定します。

誰のため？

初めてJDAサイトを見る人と、大会の実在感を写真から知りたい人。

何を最初に？

大会写真そのもの。説明を読ませる前に、現場の空気を伝える。

何を残す？

既存ヘッダー、ページ構造、ブランド配色、現在の操作体系。

何を削る？

写真タイトル、大会情報、イベントリンク、写真を邪魔する常設テキスト。

何を守る？

元写真、既存ページ、更新の再現性、失敗時にも使えるサイト本体。
